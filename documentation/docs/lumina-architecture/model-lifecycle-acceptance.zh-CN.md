# lumina 模型生命周期验收和需求追踪

本清单约束[完整升级计划](./model-lifecycle-master-plan.zh-CN.md)的真实交付。下列用例当前全部为 NOT_RUN，需在对应工作包实施后执行。计划覆盖率与功能通过率分别记录；存在计划不代表模型已验证。

## 证据规则

每条记录包含 caseId、工作包、源码 SHA、产品版本、Runtime build/feature/摘要、操作系统与硬件、真实 ModelScope 仓库和不可变版本、文件摘要、LaunchConfig 摘要、测试输入、真实输出引用、测量值、判定、执行者与时间。

状态取 PASS、FAIL、NOT_RUN、BLOCKED、NOT_APPLICABLE。后两者必须有原因和原需求对应说明；不得把缺硬件、无模型、ignore、超时或跳过算 PASS。NOT_APPLICABLE 只适用于具体组合无此可选组件，不能用来免除整个要求模型类别。

解析器、状态机和故障恢复的确定性验证可以使用明确的格式样本及故障注入，不构成推理成功证据。所有模型能力和产品端到端验收必须使用真实权重、真实引擎、真实工具和真实输出，禁止 Mock 推理、虚构文件或假成功响应。

## 全类别真实能力验收

每类至少一个真实 ModelScope 全 GGUF 代表组合通过完整搜索、计划、安装、启动、验证和使用链路。LLM 同时覆盖 Dense 与 MoE，文件格式同时覆盖单文件与分片；VLM 至少包含一次真实跨仓库正确配对及错误配对反例。适用该用例但没有模型来源时是 BLOCKED，整个类别仍未完成。

验证分两层：本机安装后 smoke 验证决定该 profile 的本机 READY；发行级能力套件检验内容质量和支持档案。两层都记录真实输出，安装 smoke 不能借用另一台机器的质量证据冒充本机运行成功。超时按 profile 和硬件定义，超时记录资源/任务失败，不直接判模型架构不兼容。

以下是计划采用的初始发行门槛，M0 固定输入集合和标准后登记版本；调整门槛必须在新一轮结果产生前记录原因，不允许看结果后降低要求以制造通过。

## 发布和项目关闭

1. 每个阶段版本只声明实际通过的模型组合和平台，并包含剩余阻塞及故障恢复说明。
2. 架构主体通过 M1 至 M3 不代表音视频目标完成；所有目标类别仍需 M4 对应工作包和真实验收。
3. 全量关闭须 48 工作包 VERIFIED、64 用例按组合完成必要覆盖、硬性要求无未解决阻塞、所有类别有真实代表安装与使用证据。
4. 不适用仅限具体组合的可选功能。例如纯文本模型不需要视觉验收，但不能据此免除 VLM 类别。
5. 发布证据归档源码 SHA、干净工作区、工具链、构建和依赖版本、安装包哈希、Runtime 描述、模型来源与哈希、测试结果和已知限制。
6. 保持仓库既有发行清单和构建来源要求；本计划不自动开放发布开关，也不把规划完成当成商用就绪。

维护节奏：每个实现变更更新任务和用例状态；每次 Runtime、规则或 SDK 变更复核证据失效范围；每次发行重新核验支持矩阵、真实来源、迁移及回退。新增模型不能只加名称，必须补齐来源、完整依赖、能力记录和实际验证。
